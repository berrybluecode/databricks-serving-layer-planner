Financial decision support

We are spending €X on Databricks. What measurable value comes back?

Cost is forecast from consumption. Value is entered as business outcomes and then classified so a CFO can see cash, avoidance, capacity, margin, and risk separately. Hours × salary is never treated as money in the bank.

Research, not folklore

How time becomes euros — and when it must not

The default recapture and risk haircuts below are published consulting methods. Change them when you have a measured realization study. Until then, keep them conservative.

Gartner 2025

Time saved is not money saved

74% of CFOs report employee time savings from AI. Only about 11% report financial value in 2025; roughly 5% cite cost savings and 6% cite revenue or profit. Hung LeHong: an extra 20 minutes a day is not financial value unless the company restructures the process or the team. Productivity leakage is often 10–30% by role — higher for executives, lower in queue-driven work such as contact centers.

Sources: Gartner Business Quarterly 1Q26; Gartner CIO conference coverage of LeHong & Vogel; Gartner “How to Turn AI Productivity Leakage Into Meaningful Financial Returns” (ID 8331717).

Gartner GenAI value

Leading indicator vs P&L result

Most early GenAI benefits are leading indicators: cycle time, quality, junior upskilling, employee experience. They become money only when used to reduce headcount or contractors, defer hiring, use more junior staff, cut service providers, or improve retention and conversion. “Do more with the same headcount” is cost avoidance, not a cost reduction.

Source: Gartner, “How to Calculate Business Value and Cost for Generative AI Use Cases” (ID 5188263).

Forrester TEI

Recapture, burden, risk, NPV

Valued hours = Hours saved × productivity recapture Productivity € = Valued hours × fully loaded hourly rate × (1 − benefit risk)

Standard TEI recapture is 50% (30% appears in loosely coupled BI studies; 70% when a task is fully automated). Burden on salary is 35%. Benefits are risk-adjusted down 10–20%. Three-year present value uses a 10% discount rate. Flexibility is recorded, not booked as cash.

Sources: Forrester Total Economic Impact methodology; published TEI studies for Power Platform (50% recapture, 15% risk, 10% PV), KNIME (30% recapture), GitHub (50% recapture), Witboost (50%, 35% burden).

Labor economics

Fully loaded rate, not sticker salary

Hourly economic value ≈ (base + employer social charges + benefits) / productive hours

Eurostat labour-cost statistics put the 2024 EU average near €32/hour and Germany near €41/hour for the whole economy. Knowledge-worker fully loaded cost is higher. This planner defaults to €55/hour as a Western/Central Europe analyst-class planning figure. Replace it with Finance’s loaded rate. Productive hours default to 220 days × 8 hours.

Source: Eurostat labour cost surveys; Forrester TEI 35% burden convention.

Open FAIR / NIST

Risk is expected loss, not a slogan

Risk-adjusted value = incidents/year × € impact × Δ probability × realization

Unpriced “better decisions” stay leading indicators. Only enter €/decision when Finance has priced cycle time (for example working-capital days or campaign perishability).

Combination rules — avoid double counting

Never add unlike benefits into one cash number

Cash-like = Hard savings + Cost avoidance Economic value = Cash-like + Recaptured productivity + Revenue margin + Risk-adjusted value Budget ROI = (Cash-like − Platform cost) / Platform cost TEI-style ROI = (Economic value − Platform cost) / Platform cost BCR = Economic value / Platform cost Payback months = (Implementation + annual platform cost) / (Economic value / 12) NPV₃ = Σ (Net economicₜ / (1 + WACC)ᵗ)

The same hour cannot be productivity and avoided hiring. Gross revenue is never added to savings — only contribution margin. Theoretical hours × wage is shown and then excluded. TCO is platform + implementation. EVA is appropriate only when Finance assigns capital; this planner stops at NPV/IRR/TCO.

Evidence-backed planning

Different workloads require different units.

The planner never silently converts tokens, DBUs, warehouse concurrency, and storage into one another. Every conversion is visible and editable.

AI

Genie products

Forecast from observed DBUs per active user per month by surface. Price Genie on the serverless real-time inference SKU. Apply the 150 DBU/user/month allowance and the One/Agents promo separately from SQL warehouse cost.

BI

AI/BI

Project executed queries from viewers, complexity, and concurrency. Caching is inside the observed DBU/query rate — do not ask for cache-miss share.

AP

Databricks Apps

Combine provisioned app instance-hours with separately metered AI and SQL dependencies. Medium is 0.5 DBU/hour; Large is 1 DBU/hour.

SKU

Two DBU prices

SQL warehouses use the SQL SKU (~$0.91 here). Genie uses serverless real-time inference (~$0.07–$0.084). Applying one list price to both overstates Genie by about 11–13×.

Calculation reference

Formulas behind every estimate

Values are calculated month by month. Month m starts at zero, so Month 1 uses the baseline and Month 12 applies eleven periods of compound growth.

Shared growth model

Monthly demand

Demandₘ = Baseline × Mix intensity × (1 + Growth%)ᵐ

Genie mix is light / regular / power users (p90 is 8–15× median). AI/BI and Apps still use 0.7× / 1.0× / 1.5× demand.

Genie One · Agents · Code

DBUs per active user

Gross Genie DBUs = Users × Mix × DBU/user/month × Language factor Language factor = 1 + Non-English% × (2.9 − 1) Free DBUs = min(Gross, Users × 150) during post-promo, or all human One/Agents DBUs during promo Billed Genie DBUs = max(0, Gross − Free) × promo metering

Calibrate DBU/user/month from system.billing.usage using genie.surface and run_as. Billing rows have no token counts.

Genie commercial model

SKU split and free tier

Genie list cost = Billed Genie DBUs × SRTI list price SQL list cost = SQL DBUs × SQL list price Would-be cost = Gross Genie DBUs × SRTI list price + SQL list cost

Do not apply the SQL warehouse price (~$0.91) to Genie DBUs. Read both prices from system.billing.list_prices. GENIE_FREE_USAGE has no list price. API / service principals get no 150 DBU allowance.

AI/BI

Queries, volume, and complexity

Queries = Viewers × Sessions/Day × Queries/Session × Active Days + Refresh Queries Volume Factor = max(0.25, √(Scanned GB / Profile Reference GB)) SQL DBUs = Queries / 1K × Profile DBU Rate × Volume Factor Peak Concurrency = Peak QPS × p95 Runtime Seconds

Profiles: Light KPI tiles, Medium multi-join dashboards, Heavy wide scans/write-back, and Extreme shared app + ETL warehouses. Cache hit rate is not a customer input.

Databricks Apps

Runtime and dependencies

App DBUs = Instances × Hours/Day × Active Days × DBU/Instance-Hour SQL Queries = Users × Requests/User/Day × Active Days × Queries/Request SQL DBUs = SQL Queries / 1K × Complexity Rate × Volume Factor Total DBUs = App DBUs + SQL DBUs + Optional Lakebase DBUs AI Tokens = Requests × (Input Tokens + Output Tokens)

Medium uses 0.5 DBU per running instance-hour; Large uses 1 DBU. Lakebase is enabled only for write-back, state, or OLTP patterns.

Workspace calibration

Observed rate, weighted by evidence

Source DBU = Σ Warehouse DBU/day × Source Task-ms ÷ Warehouse Task-ms w = Observed Queries ÷ (Observed Queries + k) Rate = w × Observed DBU/1K + (1 − w) × Preset DBU/1K

Task-time attribution removes shared-warehouse distortion. P10 and P90 daily rates produce the cost band. k defaults to 5,000 queries.

Commercial model

List price, discount, and net cost

SQL List Cost = SQL DBUs × SQL List Price Genie List Cost = Billed Genie DBUs × SRTI List Price Discount Savings = Total List Cost × Discount Rate Net Cost = Total List Cost − Discount Savings

This deployment defaults to Azure North Europe SQL at $0.91/DBU and Genie SRTI at $0.084/DBU. The app overwrites those from system.billing.list_prices when it can.

Workspace calibration

How observed workloads improve the estimate

When this planner runs as a Databricks App, Calibrate from workspace pulls 7–90 days of system tables. For Genie it measures DBUs per active user per month by surface from billing. For SQL it still attributes warehouse DBUs by task time. The static GitHub Pages build cannot do this.

  1. 1. Classify the SQL to a source

    Each statement in system.query.history is tagged as a dashboard, Genie space, or App. Dashboards use query_source.dashboard_id. Genie uses query_source.genie_space_id. Apps use executed_as = the App service-principal client ID, which equals usage_metadata.app_id in system.billing.usage.

    App SQL always runs as that service principal, so the planner can measure cost per query but not requests per user.

  2. 2. Split shared warehouse DBUs by task time

    A naive warehouse DBU ÷ query count is misleading when Apps, dashboards, Genie, and ETL share a warehouse. Each day’s warehouse DBUs are allocated by compute time:

    Source DBU/day = Warehouse DBU/day × Source task-ms/day ÷ Warehouse task-ms/day Observed DBU / 1K = Σ Source DBU ÷ Σ Source queries × 1,000

    Idle warehouse time that day is shared by whoever ran queries. That is a real cost. In the DQX demo workspace this dropped dqx-studio-v2 from a naive 702 DBU / 1K to an attributed 49.5 DBU / 1K.

  3. 3. Blend observation with the complexity preset

    A 15-query dashboard should not overwrite the Medium preset. Credibility weighting keeps small samples close to the planning default:

    w = n ÷ (n + k) Rate used = w × Observed DBU/1K + (1 − w) × Preset DBU/1K

    n is observed queries. k defaults to 5,000 and is editable. 50 queries give about 1% weight to the observation. 100,000 queries give about 95%. The volume factor still applies to the preset half of the blend.

  4. 4. Show a P10–P90 cost band

    Daily observed rates vary. The same blend is run once with the 10th-percentile daily rate and once with the 90th. Those two forecasts become the 12-month cost range under the headline number.

    Low cost = forecast using blended P10 DBU / 1K High cost = forecast using blended P90 DBU / 1K

    Recalibrate monthly. Investigate if the observed rate moves more than 15% from the last calibration.

Calibration loop

Replace assumptions with actuals.

  1. Start with a light, regular, or power user mix and the complexity preset that matches the workload.
  2. In the Databricks App, calibrate Genie from billing (DBU/user/month by surface) and SQL from query history.
  3. Keep user counts as planning inputs. Do not ask customers for cache-miss share or token-to-DBU conversion.
  4. Confirm SQL and Genie SRTI list prices separately in system.billing.list_prices.
  5. Recalibrate monthly and investigate forecast variance above 15%.
